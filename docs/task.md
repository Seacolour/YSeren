# YSeren 项目推进计划

## 1. 项目定位

一句话定义：

`YSeren` 是一个面向局域网场景的本地媒体快开工具。用户只需要一个可执行文件和一个配置文件，就能把本地目录快速变成可在另一台设备浏览、搜索和播放的网页入口。

这个项目的价值不在于“功能更多”，而在于：

- 更轻：单程序文件 + 配置文件即可运行
- 更快：启动后立刻可访问，不需要搭建完整媒体中心
- 更直接：以“共享和播放本地文件”为唯一主线

## 2. 产品边界

### 2.1 必须坚持的范围

- 只解决本地媒体目录在局域网内的浏览、搜索和播放
- 优先保证手机浏览器和桌面浏览器直接可用
- 保持“配置简单、启动简单、理解简单”
- 允许与 `nginx`、`Caddy`、域名、HTTPS 等外部工具配合

### 2.2 明确不做的范围

- 不做影视库管理
- 不做刮削、海报墙、元数据匹配
- 不做账号体系、权限体系、多人管理
- 不做转码、转封装、字幕平台化能力
- 不做内置公网穿透、内置域名、内置反向代理
- 不追求“万能流媒体服务器”定位

### 2.3 仍然要保留的底线保护

不做复杂安全体系，不等于放弃所有基础保护。以下内容应继续保留：

- 配置校验
- 路径安全校验
- 明确的错误提示

这些保护不是为了把项目做重，而是为了避免工具误伤用户数据。

## 3. 当前能力盘点

目前项目已经具备首个公开版本的基础能力：

- 单可执行文件交付，前端可嵌入后端产物
- YAML 配置加载
- 多个资源目录挂载
- 目录树浏览
- 媒体文件搜索
- 浏览器直接播放音视频
- 局域网访问地址输出
- 前端基础导航和播放状态恢复

这意味着项目当前最需要的不是继续扩功能，而是：

- 统一定位
- 打磨开源首发材料
- 补齐最小质量保障

## 4. 推进原则

后续所有需求都用下面 4 条原则筛选：

1. 这个需求是否能明显提升“30 秒内把本地视频共享给另一台设备播放”的体验？
2. 这个需求是否会让程序从“单文件工具”滑向“平台型产品”？
3. 这个需求是否可以交给更成熟的外部工具来解决？
4. 这个需求如果不做，会不会影响首个公开版本的可用性和可信度？

如果第 1 条回答是否定的，通常就不应该做。

## 5. 阶段规划

### Phase 0：开源首发准备

目标：把项目整理到“可以放心放到 GitHub 上让别人理解和使用”的状态。

- [ ] 统一项目命名
  完成标准：对外统一使用 `YSeren` 作为工具名称；默认配置文件名使用 `yseren.yaml` / `yseren.yml`。

- [ ] 保持 README 聚焦使用说明
  完成标准：README 主要包含功能描述、快速开始、配置示例、构建方式、访问方式，不把路线图和大量设计讨论塞进去。

- [ ] 提供开源首发必备资料
  完成标准：至少准备好 `LICENSE`、示例配置文件、项目截图或 GIF、首版发布说明。

- [ ] 补齐项目介绍的一致性
  完成标准：项目名称、功能边界、适用场景、非目标在 README、文档、发布页中的说法一致。

### Phase 1：核心质量加固

目标：在不扩大战线的前提下，让核心链路更稳。

- [ ] 为关键后端逻辑补充单元测试
  建议优先覆盖：配置加载、路径安全、URL 编码、目录树过滤、缓存逻辑。

- [ ] 完成最小自测清单
  完成标准：至少验证 Windows 本机、手机浏览器、局域网另一台设备三种访问方式。

- [ ] 优化启动失败和配置错误提示
  完成标准：让首次使用者能在 1 分钟内判断出是配置问题、路径问题还是端口问题。

- [ ] 复核大目录场景体验
  完成标准：确认扫描、搜索、刷新在常见个人媒体目录下仍可接受，不追求极端性能优化。

### Phase 2：轻量体验打磨

目标：只做真正增强主线体验的小改进。

- [ ] 梳理文件浏览体验
  可选方向：排序规则、空状态文案、刷新入口、当前目录感知。

- [ ] 梳理播放器体验
  可选方向：错误回退、移动端样式、播放状态反馈。

- [ ] 梳理配置体验
  可选方向：示例配置更完整、字段注释更清晰、默认行为更直观。

说明：这一阶段只做“小而确定”的体验改进，不引入新系统级能力。

### Phase 3：外围集成文档

目标：把复杂场景交给外部工具，但给用户留出清晰接入路径。

- [ ] 增加反向代理示例文档
  建议涵盖：`nginx`、`Caddy` 的最小配置示例。

- [ ] 增加公网访问说明
  建议涵盖：域名、HTTPS、端口暴露、风险提示。

- [ ] 增加运行方式说明
  建议涵盖：命令行启动、开机自启、作为后台服务运行的常见方式。

注意：这里是“写文档”，不是把这些能力内置进程序。

## 6. GitHub 首发前清单

建议把下面这些项目视为首发前的最小门槛：

- [ ] `go build ./...` 可通过
- [ ] 前端构建流程可通过
- [ ] README 可让陌生用户完成首次启动
- [ ] 有可直接复制的配置示例
- [ ] 有明确许可证
- [ ] 有至少一张运行截图或短 GIF
- [ ] 有首版发布说明
- [ ] 项目命名一致，不让用户困惑

## 7. 首个公开版本建议目标

建议把首个公开版本定义为 `v0.1.0`，并明确它只承诺下面这件事：

“用户可以通过一个程序文件和一个配置文件，把本地媒体目录稳定地共享到局域网，并在另一台设备的浏览器中浏览、搜索和播放。”

只要这件事做到了，`v0.1.0` 就是成立的。

## 8. 暂不推进事项

以下内容除非未来定位发生变化，否则不建议进入近期计划：

- 用户系统
- 权限控制
- 在线转码
- 元数据抓取
- 自动分类
- 电视端专用客户端
- 云同步
- 内置公网穿透
- 内置 HTTPS 方案

## 9. 维护策略

建议采用“轻维护、慢迭代”的策略：

- 优先修复影响核心链路的问题
- 谨慎新增功能
- 新功能必须服务于主线场景
- 能写成文档的能力，尽量不写进程序
- 能交给成熟外部工具的能力，尽量不在项目内重复实现

如果以后某个需求让项目明显偏离“单文件局域网媒体快开器”定位，就应该优先拒绝，而不是默认接收。
